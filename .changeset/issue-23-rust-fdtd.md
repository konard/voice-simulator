Render the 3D FDTD tiers in the Rust engine (issue 23). The voxel-model solver `Fdtd3d` is ported to `crates/voice-simulator-core/src/fdtd/` (`kernel.rs`, `kernel_simd.rs`, `model.rs`, `solver.rs`) and plugged into the renderer through the `Solver` trait of issue 22; JavaScript still builds the voxel model and packs it once into one buffer (`packVoxelModel` of `src/engine/pack-model.js`). `RustVoiceRenderer` and `renderPlanRust` now take `solver: 'fdtd3d'` (the tiers `high` to `reference`, in a room too); `solver: 'fdtd2d'`, a WebGPU `device` and `source: 'folds'` still throw `ENGINE_UNSUPPORTED`. The kernel has three bit-identical forms (the scatter loop of `#stepJs`, a gather over padded incident lists, and the scatter without the flux store that the solver runs), each also with WebAssembly SIMD (`f64x2` multiply and subtract only). `npm run build:wasm` builds a second file with `+simd128`, and `loadEngineModule(url, { simd })` loads it with `simd: 'auto'` when it is shipped and falls back to the scalar file. Measured with `REQUIRE_WASM=1 node --test tests/rust-fdtd.test.js`: the kernel, the SIMD kernel and JavaScript agree under `===` over 2000 steps; renders of `'Hello.'` at `high` differ by at most 0 (1.1e-19 with `teeth: false`, 0 in a 40 cm room). `voice-simulator-cli render-job` of a `high` job prints the same SHA-256 as the WebAssembly render. The heavy test `performance-rust-fdtd` measured the Rust scalar renderer 1.43, 1.11 and 1.12 times faster than JavaScript on `high`, `ultra` and `studio` (identical samples); the SIMD build was 1.06 times faster than the scalar one on `high`, below the 1.15 required, so it is built and tested but not shipped (`SHIP_SIMD` of `scripts/build-wasm.mjs`). The WebAssembly file is 184968 bytes against a new budget of 196608.
